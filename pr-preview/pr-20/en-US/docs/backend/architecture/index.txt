# Backend architecture

The OpenMRS backend is a Java web application. [openmrs-core](https://github.com/openmrs/openmrs-core) provides the data model, the service layer and the module framework. Everything else, including the REST and FHIR APIs that O3 calls, is a module. A distribution such as the [Reference Application](https://github.com/openmrs/openmrs-distro-referenceapplication) chooses which backend modules, which frontend modules and which metadata ship together.

This page gives you the map you need to read a stack trace, find the code behind an endpoint, or work out which module to install.

## openmrs-core

The repository is a Maven project with a handful of modules. The two you will read most are:

- **`api`** holds the domain classes (`org.openmrs.Patient`, `Encounter`, `Obs`, `Concept`, and so on), the service interfaces in `org.openmrs.api`, their implementations in `org.openmrs.api.impl`, the Hibernate data access objects in `org.openmrs.api.db.hibernate`, the module framework in `org.openmrs.module`, and the Liquibase changesets that create and migrate the database.
- **`web`** holds the web layer: the startup listener, the dispatcher servlet that serves `/ws/*`, the servlet filters and the setup wizard. The `webapp` module packages it, with the legacy views, into the `openmrs.war` that Tomcat runs.

### The service layer

Every operation on data goes through a service. `PatientService`, `PersonService`, `EncounterService`, `ObsService`, `ConceptService`, `OrderService`, `VisitService`, `LocationService`, `FormService`, `ProgramWorkflowService`, `ProviderService`, `UserService` and `AdministrationService` are the ones you will meet.

The services are Spring beans with method-level security. Most methods declare the privilege they need, with `@Authorized` on the 2.x line and Spring Security's `@PreAuthorize` on `master`, and an interceptor checks the current user before the method runs. That is where authorization happens for anything that calls the services, including the REST API. The FHIR2 module applies the same privileges in its own data access objects, as described below. [Privileges and roles](/docs/backend/privileges-and-roles) covers this in detail.

Under each service is a DAO interface and a Hibernate implementation, for example `PatientDAO` and `HibernatePatientDAO`. You rarely need to go that deep, but when a search behaves unexpectedly the query is in the DAO.

### The data model

Persisted objects implement `OpenmrsObject`, which gives most of them an integer `id` used for database joins and a `uuid` used everywhere else. A few, such as `Role`, are keyed by name instead. The APIs normally identify objects by UUID, and the UUID is what the frontend stores and passes around.

Two base classes matter because they decide how deletion works:

- **Data** (`BaseOpenmrsData`): patients, encounters, observations, visits, orders. Data is **voided**, never deleted in normal operation. A voided object carries `voided`, `dateVoided`, `voidedBy` and `voidReason`, and is excluded from queries unless you ask for it.
- **Metadata** (`BaseOpenmrsMetadata`): encounter types, locations, forms, identifier types. Metadata is **retired**, as are other retirable objects such as `Concept`, which has its own base class. A retired object stays valid for existing references but shouldn't be used for new ones, so a retired encounter type still shows on old encounters but is hidden from the picker. Roles and privileges extend `BaseOpenmrsMetadata` too, but they can't be retired, only deleted.

Both kinds also carry `creator`, `dateCreated`, `changedBy` and `dateChanged`, which the REST API exposes as `auditInfo` in the `full` representation.

Hibernate mappings are a mix of JPA annotations on the classes and `*.hbm.xml` files under `api/src/main/resources/org/openmrs/api/db/hibernate/`. The database schema is built by Liquibase changesets in `api/src/main/resources/org/openmrs/liquibase/`.

[Data model](/docs/backend/data-model) explains the main objects and how they relate, and the [OpenMRS data model reference](https://om.rs/dm) documents the tables and their columns.

## Modules

A module is a jar with an `.omod` extension and a `config.xml` at its root. The descriptor declares the module's id, version, the core version it requires (`require_version`), the modules it depends on (`require_modules`), its activator class, and the privileges and global properties it adds. On start, openmrs-core gives each module its own class loader, runs its activator, and refreshes the Spring context so the module's beans and controllers join the application.

Modules are loaded from the `modules` folder of the application data directory, which is `/openmrs/data` in the Reference Application's Docker image and `~/openmrs/<serverId>` with the SDK. When nothing sets it, OpenMRS uses `~/.OpenMRS` on Linux and macOS, and on Windows `Application Data\OpenMRS` in the user's home folder if that exists, otherwise `%APPDATA%\OpenMRS`.

The Reference Application pins its backend modules in [`distro/distro.properties`](https://github.com/openmrs/openmrs-distro-referenceapplication/blob/main/distro/distro.properties). The ones O3 depends on most:

- **`webservices.rest`**: the REST API at `/ws/rest/v1`
- **`fhir2`**: the FHIR R4 API at `/ws/fhir2/R4`
- **`initializer`**: loads metadata and configuration from files on startup
- **`idgen`**: generates patient identifiers
- **`emrapi`**: higher-level clinical operations and the EMR API configuration the frontend reads
- **`queue`**: service queues
- **`appointments`**: appointment scheduling (Bahmni's module)
- **`o3forms`**: REST endpoints that return a form schema with its subforms, translations and concept metadata resolved, for the React form engine
- **`legacyui`**: the old server-rendered admin pages at `/openmrs/admin`

Other frontend modules depend on `cohort`, `patientflags`, `stockmanagement`, `billing`, `bedmanagement`, `attachments`, `patientdocuments`, `reporting` and `ordertemplates`. Check `distro.properties` for the current list and versions, and browse [OpenMRS Add Ons](https://om.rs/modules) for modules the Reference Application doesn't ship. A frontend module declares the backend modules it needs in its `routes.json`, as described in [Declaring backend dependencies](/docs/frontend-modules/overview#declaring-backend-dependencies).

## REST and FHIR: the two API layers

Both APIs are modules on top of openmrs-core, but they reach the data differently. The REST module calls the core services, so it gets their privilege checks and business rules. The FHIR2 module has its own services and data access objects, which enforce core privileges but write through Hibernate directly, so core service rules, such as the patient service's identifier checks, don't run for FHIR writes.

- The **REST module** maps each OpenMRS class to a resource class that decides which properties each representation exposes and which can be set. It covers nearly the whole data model, including administrative metadata. Read [REST API](/docs/backend/rest-api).
- The **FHIR2 module** translates between OpenMRS objects and FHIR R4 resources, so it covers clinical data well and administrative data barely at all. Read [FHIR API](/docs/backend/fhir-api).

`openmrsFetch` in `@openmrs/esm-framework` works with both. `restBaseUrl` is `/ws/rest/v1` and `fhirBaseUrl` is `/ws/fhir2/R4`, and both are relative to `window.openmrsBase`, which is `/openmrs` in a standard deployment.

The Reference Application builds its backend and frontend separately, as two images, so that each can be rebuilt on its own. That's a choice rather than a requirement: the SDK's `build-distro` goal can run the frontend assemble and build steps too. The backend build reads `distro.properties`, resolves the core WAR, every module and every content package from Maven, and lays them out so that Tomcat finds the WAR, the module loader finds the `.omod` files, and Initializer finds the configuration. The frontend build reads `spa-assemble-config.json`, downloads each frontend module from npm, and produces the import map and routes registry the app shell loads.

Content packages carry configuration for both halves. A package such as [`openmrs-content-referenceapplication`](https://github.com/openmrs/openmrs-content-referenceapplication) is a zip of Initializer files under `configuration/backend_configuration/` plus a frontend `config.json` under `configuration/frontend_configuration/`. In the Reference Application only the backend half is used, because the frontend image serves the distro's own `frontend/config-core_demo.json` instead. [Metadata and Initializer](/docs/backend/metadata-and-initializer) explains how the backend files load.

## Which versions you're working against

The Reference Application currently ships openmrs-core 2.8.x. The `master` branch of openmrs-core is 3.0.0-SNAPSHOT and has moved to Java 21, Spring 7, Hibernate 7 and the Jakarta servlet API. Module authors are tracking it, and the REST module's `master` already builds against it, but the released modules you run against today target the 2.x line. Where this section describes a mechanism that differs between the two, it says so.
