Key backend repositories

The backend that O3 talks to is spread across a number of community-maintained GitHub repositories, in the same way the frontend is. Each one is focused on a particular concern: openmrs-core owns the data model and services, each module adds an API or a feature on top, and the distribution and content repositories decide what ships together. This page lists the ones you’re likely to open while working on a frontend module. Key repositories covers the frontend side.

Core and the APIs

  • openmrs-core  - the API and web application: the data model, the service layer, the module framework, and the Liquibase changesets that build the database. Start here when you need to know what a privilege gates or how an object is validated.
  • REST Web Services  - the REST API at /ws/rest/v1. The @Resource classes under omod/src/main/java define every representation and every creatable property.
  • FHIR2  - the FHIR R4 API at /ws/fhir2/R4. Resource providers and translators live under api/src/main/java.
  • Initializer  - loads metadata and configuration from files on startup. The readme/ folder has one document per domain.

Modules the Reference Application ships

The current list is in distro/distro.properties and the versions are in distro/pom.xml. The ones frontend modules depend on most:

  • EMR API  - higher-level clinical operations and the EMR API configuration that useEmrConfiguration() fetches, such as the primary identifier type and the admission encounter type.
  • ID Generator  - patient identifier generation, used by patient registration.
  • Queue  - outpatient queue management behind the service queues app.
  • Appointments  - Bahmni’s appointment scheduling module, behind the appointments app.
  • O3 Forms  - REST endpoints that return a form schema with its subforms, translations and concept metadata resolved, for the React form engine.
  • Cohort  - the enhanced cohort data model behind patient lists.
  • Patient Flags  - flags that mark a patient record with a message, shown just below the patient banner when the patient-flags feature flag is on.
  • Attachments  - upload, storage and retrieval of files attached to a patient.
  • Patient Documents  - printable documents such as patient reports, summaries and receipts, built on the Reporting module.
  • Bed Management  - beds, admission locations and the rest of the inpatient data model behind the ward app.
  • Stock Management  and Billing  - the backends for the stock management and billing apps.
  • Order Templates  - REST services for order templates, used by the medication order form when the ordertemplates-module feature flag is on.
  • Reporting  and Reporting REST  - report definitions and the REST layer over them.
  • Tasks  - the FHIR-backed task list.
  • Authentication  - extended authentication such as two-factor login.
  • Open Concept Lab  - imports concept collections from OCL, which is how the Reference Application loads CIEL-sourced concepts.
  • Address Hierarchy  - constrained address fields and the hierarchy behind the address form.
  • Metadata Mapping  - metadata sets and term mappings that other modules look up by code rather than UUID.
  • Reference Demo Data  - generates the demo patients, visits and observations on a fresh server.
  • Legacy UI  - the server-rendered administration pages at /openmrs/admin.

Distribution and metadata

  • Reference Application distro  - pins the backend modules and content packages, builds the Docker images, and holds the docker-compose.yml that runs the whole stack.
  • Content: Reference Application  - the minimum metadata to run O3.
  • Content: Reference Application demo  - the starter-kit metadata: locations, encounter types, forms, programs and queues, plus a frontend configuration that the Reference Application’s own frontend image doesn’t use.

Tooling and documentation

  • OpenMRS SDK  - the Maven plugin that sets up and runs OpenMRS servers locally. Its documentation is on the wiki .
  • OpenMRS Add Ons  - the directory of published modules, for anything the Reference Application doesn’t ship.
  • REST API docs  - the source of rest.openmrs.org .
  • OpenAPI Maven plugin  - generates an OpenAPI 3.1 document for any module’s REST resources at build time. Still in development.
  • OpenMRS data model reference  - a browsable reference for the tables and their columns, generated from the database schema.
  • OpenMRS FHIR documentation  - the community’s FHIR strategy, the FHIR squad and the FHIR2 module’s history.
